## Flow and persistence

Story → human-approved angle and exact approved script revision → supplied creative brief → reviewed asset candidates → optional manual ChatGPT/Canva handoff → approved creative specification → registered renderer → human output review → existing platform package/final approval/outbox.

`src/creative/schema.ts` defines strict version-1 CreativeBrief, VisualSpec, CarouselSpec/Scene, CaptionSpec, MotionSpec, AssetRequirement/Candidate and handoff contracts. Extensions carry future data without silently accepting misspelled core fields. Scene types describe editorial purpose, not layouts. Each scene has independent composition, hierarchy, typography, optional palette, assets and retained evidence references. Static and motion specs share scene IDs and exact copy. There is no default creative palette or accent; predominantly light compositions can be specified per story. No copy or visuals are generated by this implementation.

Records use `control_entities.kind=creative`, the existing epoch/transaction/history mechanism and private control API. Every package binds content ID/version, story, approved angle and exact current approved draft revision. `creative_save` creates revision 1, or a new brief revision for an existing record, clearing creative approval. Previous snapshots remain in existing immutable control history. A new revision must explicitly replace or reselect external assets; old handoffs cannot silently carry forward. Changed content/draft/brief, missing approval or mismatched media makes render eligibility fail closed. This is independent of the existing editorial and production state machines.

## Commands and inert jobs

Existing authenticated, same-origin `POST /api/control` accepts `{ epoch, command }`. Additive commands: `creative_save`, `creative_approve` (confirmed), `creative_job_queue`, `creative_handoff_request`, `creative_canva_editing`, `creative_import` and `creative_asset_review` (confirmed). Existing payloads/routes remain unchanged.

`control_jobs.kind=creative` reserves GENERATE_CREATIVE_BRIEF, GENERATE_VISUAL_SPEC, GENERATE_CAROUSEL_SPEC, GENERATE_CAPTION_SPEC, GENERATE_MOTION_SPEC, RESOLVE_ASSET_CANDIDATES, WAIT_FOR_EXTERNAL_VISUAL, IMPORT_EXTERNAL_VISUAL, RENDER_STATIC_CREATIVE and RENDER_MOTION_CREATIVE. Keys include exact entity revision, brief revision, binding, operation and specification checksum. Repeated requests return the same job. Jobs are inspectable in the private control snapshot and start **blocked**, with explicit manual-handoff/executor-not-configured reasons. No scheduler/worker claims these jobs and no AI executor is installed. Existing cancel/retry commands remain available; recovery does not install or invoke an executor. Future executors must check `currentCreativeJob` and reacquire a valid lease before side effects.

## Manual ChatGPT / Canva

Request ChatGPT → WAITING_FOR_EXTERNAL_VISUAL. Daniel generates/selects in ChatGPT himself. No API key, ChatGPT UI automation or browser automation is used. Canva → CANVA_HANDOFF_READY → CANVA_EDITING → CANVA_EXPORT_IMPORTED. `GET /api/creative/:id/handoff` downloads private JSON with exact brief/copy/scene order, selected asset URLs/private file references, source/evidence notes, aspect ratio and supplied typography/color instructions. It does not fetch imagery or call Canva.

After Daniel explicitly approves a selection, import references an existing private upload's `media_objects` receipt via `creative_import`. Actual upload transport remains the existing private artifact/media integration; this pass adds no upload UI. The server reads the checksum, filename reference, MIME and story/draft binding from the receipt, never from caller assertions. Preserve brief ID/revision, optional prompt reference, generated timestamp (nullable when unknown), imported timestamp, creator/source (ChatGPT manual / Canva manual), human selection and usage notes. Repeated identical imports are idempotent. Imports become **rights unknown, review pending, publishable false**. `creative_asset_review` records human selection/rejection and reads existing receipt-linked editorial rights; it never clears rights itself. A selected asset must also belong to the approved draft’s asset list. Generated imagery, official media and Canva exports never acquire rights automatically.

## Assets and renderers

Provider-neutral resolver interfaces support Daniel-owned media, official/company assets, screenshots, Wikimedia, Pexels, manual imports, ChatGPT illustration and future providers. No production search/download integration is installed. Every candidate records canonical URL, author, license/basis, attribution, retrieval time, dimensions/duration, checksum when available, relevance, selection, review and rights. Selected required assets must match an existing current media receipt linked to an editorial asset with explicit cleared rights, usage basis and human clearance for this exact draft.

`CreativeRenderer` accepts the same approved package for static or motion mode, retaining scene IDs, binding, specification checksum and creative version. No renderer is registered by default. Missing rich static/motion renderer reports CREATIVE_RENDERER_NOT_CONFIGURED; it never falls back to one aesthetic. Legacy `control/graphics`, SVG, Sharp, PNG/JPEG and ordered carousel code remain working unchanged and are legacy working cards, not final DVNI templates. No Remotion dependency is added. A renderer result must remain publishable false/review required and pass existing human output and platform approval before release.

CaptionSpec stores independent Instagram, TikTok, YouTube Shorts, X and Newsletter copy (hook/body/context/CTA/source note/hashtags/alt/title/description). No platform copy is cloned or generated. A Daniel-take field references exact separately approved take text/version, bound to the content; a take scene must use that exact approved text.

## Product/public boundary

`design-system.css` remains BrainOS UI. `public-presentation.css` preserves only the **existing site appearance for compatibility**, locally scoped and independent of internal token changes. Its temporary control colors/fonts are not DVNI content defaults or an approved public grammar. This prevents an internal theme change from redesigning the public site during C#2 experimentation. `creative/tokens.ts` emits only explicitly supplied `--creative-*` palette/type roles; absent accent/palette yields no default. Renderers must consume the supplied CreativePackage and never import product UI tokens or legacy card styling. Final approved grammar plugs into this contract after C#2 validation.
